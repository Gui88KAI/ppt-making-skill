# 代表页与交付验收

本文件说明[入口](../SKILL.md)中各阶段的完成依据。AI自行检查并修复；除非用户明确要求审稿，或出现影响范围的新歧义，不增加等待审批的流程。

## 先完成实际代表页

按这套作品最容易出问题的部分选择代表页。新风格通常包含标题/主视觉关系、正文密度、互动或复杂过程；可以选封面、典型内容页、问答页，也可以由一两页覆盖。已有设计的局部修改只处理和复查受影响的页面。

代表页应包含最终使用方式下的字体、图像、底色和实际正文。提示词、线框、纯图像海报和写着版式名称的表格都不算已排好的可编辑代表页。用于找灵感的整页生图另标“视觉草图”。

先看全页，再放大检查：

- **主次与阅读**：第一眼是否落在主要内容；正文在预计观看距离是否清楚；参考稿的图文比例是否得到落实。
- **文字**：艺术字是否适合当前主题、字形是否正确、疏密是否自然；正文是否可编辑。艺术字不必用于封面或每页。
- **图像融合**：在实际深/浅背景上看四边、四角、纸底色差、白边和主体细节。批准原图后的修边不重画场景，柔边不等于完整抠图。
- **讲解顺序**：问题先展示、讨论后再出现提示；过程和对照的先后关系是否帮助理解。看静态画面不能证明点击时机正确。
- **逻辑可见性**：遮住讲稿后，标题、图文关系、箭头和留白是否仍能让观众说出本页的推进动作。
- **版式舒适度**：同类页面是否共享稳定网格、页边距和基线；图片与正文是否有各自呼吸空间，还是挤成互不相关的拼贴。
- **视觉覆盖**：若`visual_mode`为`image-led`，独立主题图位是否达到建议数量；减少图片时，是否用承担叙事的原生图示补位。

发现会扩散到全篇的问题，先修代表页再扩展。记录页码、预览文件、所用PPTX的SHA-256、渲染来源、发现的问题和修复后结果即可，不填虚构分数，不凑固定修改数量。导出文件改变后更新预览，特别核对标题和图片没有漏画。代码近似预览可用于初步设计，但保留其不确定性，导出后仍要检查实际文件。

## 计划与文件对应

沿用项目已有记录，页面规格用`pages`数组。以下是**单页记录示例，不是已生成资产**：

```json
{
  "pages": [
    {
      "page": 1,
      "purpose": "从具体经历进入讨论",
      "logic_role": "hook",
      "seconds": 90,
      "layout_family": "editorial",
      "visual_relation": "问题压住情境图，讨论提示收在底部",
      "reading_order": ["问题", "情境", "讨论后揭示提示"],
      "images_required": true,
      "asset_bindings": [
        {"slot": "scene", "image_role": "situation", "file": "assets/p01-scene.png", "shape_id": 5}
      ],
      "motion": {"entry_groups": [{"purpose": "讨论后揭示提示"}]},
      "written_motion": {"effect": "fade", "groups": [[7, 8], [9]]}
    }
  ]
}
```

`page`从1开始，`shape_id`来自当前页实际对象，组内对象也可记录。先制作再填绑定，不能照抄示例ID。`file`相对记录文件所在目录，指向实际嵌入的本地自产或获准使用文件；有压缩或去底衍生图时绑定最终嵌入文件，另保留源图。

`motion.entry_groups`只表示计划；`written_motion`仅在写入后记录。`click_fades`返回的`groups`与`effect`可用于绑定，但需重新读取最终PPTX核对。图像和动画核对可执行：

```bash
python scripts/delivery_check.py output.pptx --plan page-plan.json --brief brief.json --report delivery-report.json
python scripts/image_usage_check.py output.pptx
```

`delivery_check.py`检查实际页数与用户约束、指定图片对象的字节与源文件、基本点击淡入组的实际目标及顺序。它读取所有页的图片和动画目标；未绑定图片、未覆盖的检查项会报告。其他动画类型只能核对目标是否存在，并明确提示需要作者工具/实机核验；不能把未支持解析说成通过。没有计划时可生成实际文件清单，但不能声称已对照设计计划。

若计划声明`visual_mode: image-led`，检查工具会给出视觉图位覆盖建议：1–4页2个、5–8页4个、9–12页6个、13–15页8个；16页以上从8个起，每再增加3页加1个。统计只认承担叙事作用的图片绑定；纸纹、图标和标题字形的`image_role`分别是`texture`、`decoration`、`title-glyph`，不计入主题图片。用户限制生图次数时可在计划中说明，并以原生图示替代。

`image_usage_check.py`会逐图计算像素哈希。同套不同主题图位重复时应处理；用户指定的原图对比、证据复核或标识用途可以记录例外。原图在同一图位跨修订保留不属于同套重复。`--exclude-name-prefix`仅用于有明确理由的例外，不能漏过重复主题图。近似构图、裁切或改色仍需逐页总览检查。

脚本不检查美观，也不接受输入中“已通过”字段作为视觉或实机证据。`images_required`为真而只有提示词、占位或空绑定时不能通过图片落实检查。旧的生图`slides`数组须先整理为真实页序，不能直接冒充最终计划。

## 三类验收分别记录

| 检查层 | 实际动作 | 留下什么 |
| --- | --- | --- |
| 文件结构 | 打开最终PPTX并运行适用检查，核对页数、实际图片、文字和动画对象 | 文件路径、SHA-256、工具结果、未覆盖项 |
| 视觉审阅 | 检查每页、全套总览及修订后的重点细节；优先原生软件渲染 | 渲染软件/来源、检查页码、问题与复查结果 |
| 目标软件放映 | 在目标WPS/PowerPoint打开最终文件，检查字体、换行、透明边缘和完整点击序列 | 软件/版本、系统、同一文件哈希、覆盖页码、实际结果 |

可运行`layout_check.py`、`pptx_inspect.py`和目标为WPS时的`wps_compat.py`。脚本通过不代替视觉审阅，Pillow近似预览不代替WPS渲染，写入动画不代替放映。修改后重新导出的文件应重新核验，旧文件的放映记录不能迁移到新哈希。

没有目标软件时继续交付可编辑文件、已完成的检查结果和明确的待验证项；有动画时附独立可读的静态副本，并检查移除动画后是否有内容叠在一起。不能为了凑“全部通过”伪造截图、版本或放映结果。

## 交付前再看内容与节奏

- 讲稿和页面是否一致，更新问题后是否同时更新提示、参考回应和备注？
- 时间预算是否包含思考、发言与过渡？没有实际演练时写“计划时长”，不称已完整试讲。
- 图文密集段与留白段是否有理由；同类对照是否一致，内容变化处是否只有左右互换？
- 每个重要页面是否有`logic_role`和`visual_relation`；遮住讲稿后仍能看见本页推进动作？
- `image-led`图片覆盖是否足够；每张主题图是否绑定具体页面目的，而不是只作好看装饰？
- 按展示尺寸检查清晰度和文件体积，保留源图；不为了缩小文件把整套正文变成图片。

报告区分结构草稿、视觉试样与交付文件，列出已发现且未解决的问题，不用一个总分盖过限制。
